### RULING — allowlist vs deletion (Preston, 2026-10-26; the ruling behind R-L3-16)
"A reader removed from the allowlist (or never on it) must still be able to delete their own cloud data." Built:
the 8 private collections split `read, write` into `read, create, update: if onList() && own uid` + `delete: if
signed in && own uid`; the owner-checked deletes on `publishedArcs`, `publicProfiles`, `follows`, `buildOns` drop
`onList()` (owner conditions unchanged); `aiUsage` delete was never gated. `onList()` sites 24 → 21 (the 4 social deletes
leave it; the 8 private matches keep one each).
**Proof — STRUCTURAL ONLY.** Per match, an unlisted uid on its own doc: read / create / update → the only allow covering
them requires `onList()` → denied; delete → its own allow, `request.auth.uid == uid` → allowed. The **rules test the
ruling asks for cannot run on this machine** (no emulator, no Firebase CLI / gcloud, Node blocked): it is the Rules
Playground step in the pre-push checklist (unlisted uid: get denied, set denied, delete allowed).
**FORK → RULED option 1 (Preston, 2026-10-26).** `deleteAccountCloudData` QUERIES `publishedArcs` (authorUid),
`follows` (followerUid, targetUid) and `buildOns` (fromUid) before its batch; with those reads list-gated, Firestore
denies the query outright for an unlisted reader and nothing is deleted. Built: owner-scoped reads open to any
signed-in uid — `publishedArcs` read `onList() || authorUid == me`; `follows` read `signed in && (followerUid == me ||
targetUid == me)`; `buildOns` read's `fromUid == me` clause no longer needs the list (the public build-on clause and the
arc-author clause still do). Each of the four deletion queries' `where` constraint is exactly the owner clause, so the
query is provably allowed. Cost, accepted by the ruling: a delisted reader can still read their own published arcs,
their own edges, and their own build-ons / questions. `onList()` sites 21 → 19. Structural only, as above.
(Option 2, not built: skip the social queries when unlisted.)
The per-request rule-check limit on a large delete batch (R-L3-16a) stays on the phone check.
